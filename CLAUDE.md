# CLAUDE.md — Peter's Pizzeria

## What this project is

A single-page React app for Peter's Pizzeria, a student-run pizza operation. Mostly a static marketing site, plus a small ordering system: customers place orders from the menu, staff manage them on a live admin board. The only backend is the `api/` folder of Vercel serverless functions.

## How to run

```bash
npm install
npm run dev       # dev server at http://localhost:5173
npm run dev:api   # order API on :3010 (run in a second terminal; Vite proxies /api)
npm run build     # production build → dist/
npm run preview   # serve dist/ locally
npm test          # run the automated test suite (see Testing section below)
npm run test:watch
npm run lint      # ESLint (flat config, eslint.config.js) — must be clean
npm run lint:fix
```

## Architecture

Client-side-only SPA with manual routing (no React Router) driven by the History API. Page state lives in `App.jsx`; the URL is the source of truth for it.

### Routing

`App.jsx` holds `page` state (`'home' | 'menu' | 'blog' | 'article' | 'gallery' | 'studio' | 'order' | 'status' | 'slices' | 'admin' | 'nights'`), initialised from `window.location.pathname` on every load. Adding a page means touching five places, each failing differently: `PAGE_PATHS`/`PAGE_TITLES` in `src/utils/routes.js` (no address — falls back to home, and `routes.test.js` fails), the render switch (blank page), `Nav.jsx`'s `isDark` (unreadable nav on a dark hero), `Footer.jsx`'s `PAGES`, and the flex-column wrapper list in `index.css` (footer stops pinning to the bottom) — unless the new page reuses an existing page's wrapper class instead of its own (`nights` renders inside `.admin-page`, so it skips that last one). `Nav.jsx`'s `PAGES` carries six links plus Order Now (`slices` shows as "Community Pictures") — the nav switches to the hamburger at 1080px instead of the page layouts' 768px to make room. `admin` (order board) is reachable from a footer-bottom button, not the nav; `nights` (past-nights archive, admin-only) is linked from the admin board itself; `studio` (share-card generator) still has no UI entry point but now has an address (`/studio`). The nav's "Order Now" button goes to `order`.

**Paths** live in one table, `PAGE_PATHS` in `src/utils/routes.js` — page id → path, plus `PAGE_TITLES` for the tab/history label. Articles are the only page whose path carries data: `/blog/<slug>`, slugified from the post title and resolved back by matching that slug against `BLOG_POSTS` (by slug, not array position, so reordering posts doesn't repoint links people have already shared). `routes.js` is pure and React-free — it's also imported by `scripts/gen-sitemap.mjs` under plain Node, which is why its `import` of `posts.js` carries an explicit file extension where the rest of the app omits it. An unknown path renders home and is rewritten to `/` on mount, so a dead link doesn't leave a lie in the URL bar.

**The transition and history are separate concerns.** `nav(page, article?, opts?)` runs the directional transition (old page slides up/out, new page rises in, 260 ms); `opts.history` decides what the address bar does — `'push'` (default), `'replace'` (a redirect the visitor shouldn't have to Back through, e.g. the nights page bouncing an unauthenticated visitor to `admin`), or `'none'` (we're *responding* to Back/Forward, so the entry already exists). The push happens **where `setPage` is called, not where the tap is handled**: tapping back to the page you're leaving mid-fade cancels the timer and takes the reverse-fade path, which never navigates — pushing at the tap would leave the bar pointing at a page that was never shown.

Deep links need the SPA rewrite in `vercel.json` (`/((?!api/).*)` → `/index.html`); without it every path but `/` 404s on Vercel. The `api/` exclusion is belt-and-braces — Vercel checks the filesystem before applying rewrites — and the pattern is parsed by path-to-regexp 6.x, which accepts the inline lookahead that newer majors reject. `vite dev`/`vite preview` do the same fallback natively, so local dev needs no config.

`localStorage.pp_page2` is **gone**. The URL restores the page now, and the old key actively hurt: it meant a bookmark could land you on the admin board. App clears any leftover copy once on mount.

### Code splitting

`studio`, `slices`, `admin` and `nights` are `React.lazy` chunks (`lazyPage` in
`App.jsx`); everything on a first-time visitor's path stays in the main bundle.
The `<Suspense>` sits *inside* the ErrorBoundary, so a chunk that won't download
surfaces as the crash page rather than an unhandled rejection.

**A failed chunk poisons its route for the whole session** — `React.lazy` caches
the rejection and re-throws it on every later render. The usual cause is a
deploy landing mid-session: the hashed filename this build asks for is gone, the
404 hits the SPA rewrite, and `index.html` comes back as a module (so the import
fails on MIME type, not on a missing file). `utils/chunkReload.js` grants
**one** reload per session for this — enough to fetch the current deploy, and
guarded so a genuinely broken chunk falls through to the crash page instead of
reload-looping. `markChunkLoaded()` re-arms the retry on the next chunk that
does load. Its test proves the refusal, not just the grant.

### Crash containment and landmarks

`components/ErrorBoundary.jsx` wraps the rendered page inside `<main>`, keyed by `page:articleId` so navigating anywhere else mounts a fresh instance and clears the error (keying on `page` alone would strand a crashed article, since `page` never leaves `'article'`). The **nav sits outside the boundary on purpose** — it stays interactive under the fallback and is the actual way out. The fallback (`.crash-page`) is deliberately plain: no GSAP, no photos, nothing that could throw a second time.

The page wrapper is `<main id="main" tabIndex={-1}>` (tabIndex so the skip link has somewhere to land; `main:focus` clears the ring). Because the per-page `<footer>` now renders *inside* `<main>`, `Footer.jsx` sets `role="contentinfo"` explicitly — a nested `<footer>` is not a contentinfo landmark on its own. A `.skip-link` is the first thing in the tab order, translated off-screen until `:focus-visible` (off-screen rather than `display: none`, which would make it unreachable by Tab).

### Ordering system

- **Customer** (`OrderPage.jsx`): cart built from `MENU_DATA` (qty steppers), persisted to localStorage (`pp_cart:v2`, `pp_who:v1`, `pp_order_id`; the older `pp_cart2` same-shape key and the legacy `pp_cart` {name: qty} shape are migrated on load); on submit → POST `/api/orders`; confirmation screen shows a pickup code and polls order status every 8s. Payment stays Venmo/Zelle at pickup — no payment processing. There's no phone/Instagram contact field, and the server no longer accepts or stores one. `publicOrder()` still strips `contact` on the way out — orders written before the field was dropped can live in Redis for their 3-day TTL, and that destructure is the only thing keeping one of them out of a public response. Don't "tidy" it away.
- **Per-slice quantity caps**: each menu item allows up to `DEFAULT_MAX_QTY` (8, in `src/utils/orders.js`) units per order; an item can set a lower `maxQty` in `menu.js` (Margherita is capped at 4). Enforced in three places that all have to agree: the order-page stepper (disables `+` at the cap), `api/_lib/catalog.js` (carries `maxQty` onto each catalog entry), and `api/orders.js`'s `validateItems()` — which aggregates qty **per item name across every line**, not just within one line, since the same item can legitimately split into several lines by add-on combination (a per-line-only check is bypassable by spreading units across combinations). `clampCartQty()` in `utils/orders.js` re-caps a persisted cart on load, for a cart saved before a `maxQty` change (or a since-lowered one).
- **Per-slice add-ons**: the Add Ons category has no standalone order rows — each slice unit in the cart carries its own add-on list (chips under the slice row, one row per unit). Cart shape: `{ [name]: string[][] }` (one addon-name array per unit); identical units group into API lines `{name, qty, addons?}`. The server validates add-ons (must exist, must be Add Ons category, only on Saturday Slices lines), prices them per unit, and stores them nested as `{name, priceCents}` on the item; `itemTotalCents()` in `src/utils/orders.js` is the shared line-total. `parsePriceCents` treats `'Free'` as 0 (an add-on priced 'Free' would otherwise be unorderable) — no add-on is currently priced that way (Extra Basil moved to +50¢), but the handling stays so one can be again without a server change. Admin fire-next counts nested add-ons; status transitions out of `done`/`cancelled` are rejected (409). Add-on chips render in a real CSS grid (`.addon-unit-chips`), not a wrapping flex row — flex-wrap let a long slice label eat into the first row's width while wrapped rows fell back to the left edge, so chips never lined up with each other at any viewport width, desktop included. The grid is a **fixed `repeat(2, minmax(0, 1fr))` at every width**, not an `auto-fill` floor: auto-fill derives the count from a width threshold, so the block silently rendered 5, 3 or 1 across depending on the viewport and read as a different shape on every device. Two columns rather than four because the column is narrower than it looks — `.order-grid` is `max-width: 1100px` with a 360px summary sidebar and a 48px gap, so the chip grid tops out at ~548px, and four across there gives ~130px per chip while the longest label ("Extra Stracciatella") needs ~137px. Four across wraps that label *on desktop*, where it looks like there's room. `minmax(0, 1fr)` rather than a bare `1fr`, which would floor each track at its content's min-content width and let one long label steal its neighbour's space. Each chip stacks name over price in their own spans (`.addon-chip-name`/`.addon-chip-price`) — joined into one `name · price` run, the break landed between the middot and the price and left the name dangling. Chips wrap to a second line rather than truncate, since an ellipsis here could swallow the price; below ~390px viewport the longest label does wrap, which is the accepted trade at that width. Each Add Ons item in `menu.js` carries a `keyword` (e.g. `'stracciatella'`); `addonLabel()` in `utils/orders.js` checks it against the slice's own `desc` (case-insensitive substring) to decide whether the add-on reads as "Extra X" there (Chef's Choice already has stracciatella) or plain "X" (Margherita doesn't) — used everywhere an add-on is shown next to its slice (order page, confirmation, admin board, nights archive).
- **Slice Status** (`StatusPage.jsx`, nav link "Slice Status"): public page that shows this device's in-flight order (via `pp_order_id`) with the same live card as the confirmation (`components/OrderStatusCard.jsx`, shared by both pages — green status banner + animated timeline). Without a saved order it shows a lookup form: `GET /api/orders?find=<code-or-name>` (rate-limited 30/IP/10min) matches pickup code exactly or name by full/first/prefix, preferring the newest active order; a hit saves the id locally and polling takes over. All public order reads (`?id=`, `?find=`) are sanitized — `contact`/`notes` never leave the server except on the admin board and the POST response.
- **Admin** (`AdminPage.jsx`): password login (POST `/api/login` → HMAC token in an HttpOnly cookie; client JS never sees it, `GET /api/login` reports session state); board polls `/api/orders` every 5s; columns New → In the oven → Ready with advance buttons (PATCH); each column and the Finished list sort oldest-first (a queue reads top-to-bottom, newest at the bottom) rather than the newest-first order `listOrders()` returns. "Fire next" panel aggregates pizza counts (add-ons dimmed) across `new` orders; tab title shows waiting count.
- **Nightly totals** (`api/nights.js`, `api/_lib/nights.js`): the admin Finished list ends with a footer line — tonight's running total (sum of `totalCents` for `done` orders on the current board) and a "Close for the night" button, in the same price/status columns the rows above it use, rather than a standalone panel. Closing (`POST /api/nights`, admin-only) snapshots the whole live board — order/done/cancelled counts, the done-orders total, and a scrubbed per-order list (name, items, totalCents, status; contact/notes dropped, same rule `orders.js`'s `publicOrder()` follows) — into a permanent archive record (`pp:night:<id>` / `pp:night-index`, no TTL, unlike orders' 3-day expiry), then wipes exactly those orders (`clearOrders(ids)` in `store.js`, given the same id list just archived) so the board is empty for the next Saturday. `clearOrders` takes explicit ids rather than re-reading "whatever's live right now": an order placed in the gap between the archive snapshot and the clear call must survive on the board, not be silently destroyed alongside the ones actually captured. Orders are gone the instant this runs, so that per-order snapshot is the only place "who ordered, what, and how much" survives past tonight. Closing an **empty** board is refused with a 409 rather than archiving a zero-count record — that's the double-close race (a second admin tab whose stale poll still shows orders fires after the first tab already closed), and the client also re-fetches `/api/orders` fresh before showing its confirm dialog so the dialog never quotes stale counts. Known accepted risk: `listOrders()` caps at `MAX_LISTED` (300), so a night with more than 300 live orders would archive/clear only the newest 300, and real orders older than the newest 300 silently drop off the admin board before that. This stays far beyond legitimate volume (a night is tens of orders, and they carry a 3-day TTL), but the rate-limit raise halved the margin and the note should say so: at 240 global/10min the board can cross 300 live orders in ~13 minutes of sustained maximum intake, where the old 120 took ~25. Reaching it requires deliberate abuse rather than a busy Saturday — but one unauthenticated IP can now put 60 junk orders on the board per 10 minutes instead of 15, which is the accepted cost of not turning away a dorm. If the 300 cap is ever actually hit, raise `MAX_LISTED` rather than lowering the intake caps back onto real customers.
- **Past nights archive** (`NightsArchivePage.jsx`, page id `nights`): its own admin-only page, reached only via a minimal text link at the bottom of the admin board (deliberately not a data-bearing panel — it costs nothing until clicked) rather than a section on the board itself. On mount it checks `GET /api/login` and bounces to `admin` if not authenticated, then lists every closed night (`GET /api/nights`) newest-first — date, picked-up/cancelled counts, total. Clicking a night expands it in place to show the archived per-order detail (`formatOrderItems()` in `utils/orders.js`, shared with the admin Finished list) — no separate route or extra fetch, since the detail already came down with the list. Each row also carries a **delete** button (`DELETE /api/nights?id=`, admin-only) that erases that night from the archive permanently — this exists for trial nights closed while testing the board before opening, which would otherwise inflate the revenue history forever. It's a hard delete rather than a `hidden` flag on purpose: a hidden-but-still-counted night is exactly the confusion the feature is meant to remove. There is no undo and no recovery path — the orders behind a night were wiped when it closed, so the archive record is the last copy of them. The button arms on first click and commits on the second (same pattern as the community-wall takedown; `onBlur` disarms), and the delete/expand controls are siblings inside `.nights-list-head` rather than nested, since a button inside a button is invalid HTML. The handler reads the record before deleting so a second tab that already deleted it gets a 404 it can resync on instead of a misleading 200; `deleteNight()` drops the index entry before the record, so an interrupted delete leaves an unreferenced record (invisible) rather than a dangling index id. Deleting history deliberately does **not** touch the live board — an order taken after the night closed belongs to the next night.
- **API** (`api/`): Vercel Node serverless functions. `api/_lib/` holds shared code (underscore = not routed). Prices are recomputed server-side from `src/data/menu.js` via `api/_lib/catalog.js` — clients never set prices. Storage (`api/_lib/store.js`): Upstash Redis when `UPSTASH_REDIS_REST_URL/TOKEN` (or `KV_REST_API_*`) env vars exist, else an in-memory Map (local dev). Orders expire after 3 days.
- **Auth**: `ADMIN_PASSWORD` env var; without it, login only works in dev mode (no Redis configured) with password `admin`, and refuses in production. The session cookie is `<issuedAt>.<hmac>`, the HMAC covering `pp-admin-v2|<issuedAt>` — the timestamp is inside the signed message, which is what lets `verifyAdminToken()` enforce a real 30-day expiry (`SESSION_MAX_AGE_MS`) without storing session state anywhere. The cookie's `Max-Age` is derived from that same constant so the browser and the server stop trusting it at the same moment; the cookie's lifetime is a hint, the server-side age check is the control. Two levers for revocation: rotating `ADMIN_PASSWORD` (invalidates every session, since the HMAC key changes) or bumping the `TOKEN_VERSION` label (same effect, without changing the password). Before this the token was an HMAC over a constant string — identical on every login, valid forever, and unrevocable short of a password change.
- **Store hours**: settings at Redis key `pp:settings` (`api/_lib/hours.js`) — `mode: open|closed|auto` plus a weekly window (day/start/end, ET). `GET /api/store` is public (order page shows a closed card); `PATCH` is admin (storefront panel on the board). Order creation is enforced server-side (403 when closed) — never rely on the client check alone.
- **Availability (86 list)**: `settings.unavailable` is an array of menu item names, toggled from the admin Availability panel (`PATCH /api/store {unavailable}`; names validated against the catalog). Sold-out items grey out on the homepage specials, menu page, and order page, and the API rejects them (400). Homepage specials are derived from menu items with a `special` field in `src/data/menu.js` — don't hardcode specials in `HomePage.jsx`.
- **Post your slice** (`SlicesPage.jsx`, nav link "Community Pictures" — also reached from the footer and from a CTA on `OrderStatusCard.jsx` once an order hits `ready`/`done`): public wall of customer photos. Storage is `api/_lib/slices.js` (`pp:slice:<id>`, `pp:slice-index`, `pp:slice-quota:<orderId>`; posts live 90 days, far longer than the 3-day order TTL). Images go to **Vercel Blob** (`BLOB_READ_WRITE_TOKEN`) via a server-side `put()` — never a browser-direct upload, so every check runs before any byte is stored. Posting requires an exact **pickup-code** match (never a name match — `?find=` in orders.js matches names, which would let anyone post as anyone) against a non-cancelled order; the window is bounded by the order TTL, so a code dies with its order at 3 days. 3 photos per order, claimed through an atomic Lua check-then-INCR (`claimSliceQuota`) and released if the upload fails. Uploads are JSON with a base64 data URL — deliberately not multipart, since `readBody()` is JSON-only and this reuses `api()` unchanged. Validation order: rate limit → `Content-Length` → decode → **magic-byte sniff** (the declared type is attacker-controlled) → quota → Blob. `imageMeta()` parses JPEG/PNG/WebP dimensions, which are stored so the wall can reserve each box with `aspect-ratio` (uploads aren't in the build-time `PHOTO_RATIOS`). Client downscales to 1600px via canvas, which also strips EXIF/GPS. The composer has a single "Take a photo or choose from library" button backed by one file input with **no `capture` attribute** — mobile Safari and Chrome then open their own native sheet offering Take Photo *and* Photo Library, so the OS presents the choice rather than the UI splitting it into two buttons. Adding `capture="environment"` back would hand off straight to the camera app and silently remove the library option, which is why this was previously two separate inputs; don't re-add it to "fix" the camera. **Posts go live immediately** (`hidden: false` at creation, auto-approved — there's no pre-publish review queue). **Moderation lives on the community pictures page itself, not the admin board**: a logged-in admin visiting `SlicesPage` gets a take-down (delete) button on every photo, not just their own — `SlicesPage` detects admin state with `GET /api/login` and shows that control when true. Delete (`DELETE`) is the only moderation action exposed in the UI, and it's permanent (also removes the blob). The `PATCH {hidden}` endpoint still exists server-side (reversible hide/restore, fully tested) but nothing in the client calls it anymore — it's unused API surface, not a dead route to clean up, kept in case a reversible takedown is wanted later. **Self-delete**: a poster can remove their own photo. The upload stores `deviceHash` (sha256 of the browser's `pp_slice_device:v1` token) on the record; `DELETE /api/slices?id=` accepts either an admin cookie or a body `{device}` whose hash matches, compared with `timingSafeEqual`. `deviceHash` is stripped from both the public feed (`publicSlice`) and the admin board (`adminSlice`) — it never leaves the server. The client lists its own post ids in `pp_slice_mine:v1` purely to decide whether to *show* the button; editing that list gains nothing because the server verifies independently. Self-delete deliberately does **not** call `releaseSliceQuota` — the 3-per-order cap counts photos posted, not photos live, or post-delete-repeat would be an unlimited upload channel.
- **Takedown requests** (`api/reports.js`, `api/_lib/reports.js`): any visitor to the community wall can flag a photo — a small flag button on each tile (two taps to send, same arming pattern as the delete button), shown to everyone *except* the poster and a logged-in admin, who both already have a real delete button there. `POST /api/reports` is **deliberately unauthenticated**: the person most likely to want a photo down is the person in it, who has no pickup code, no device token for that post, and no order. Requiring any credential would lock out exactly the people the feature exists for. Records are keyed by **slice id, not report id** (`pp:report:<sliceId>` / `pp:report-index`, 90-day TTL matching slices), so ten people flagging one photo is one row on the board carrying a count, not ten rows for one decision. The record holds a list of device hashes purely to keep one person from inflating that count; `devices` is never returned by the API. The response omits the count too — echoing it would let anyone probe which photos have already been flagged. `GET`/`DELETE` are admin-only. The admin board polls `/api/reports` alongside orders and store status, but with its own `.catch()` so a failure there can't blank the order board mid-service; `ReportsPanel` **renders `null` when the queue is empty**, so it exists on screen only when something needs a decision. Because the panel sits at the *top* of the board — where nobody is looking mid-service — arrival is announced three ways, none of which requires being scrolled up: `TakedownAlert` (same module) puts a pulsing count in the header that scrolls the panel into view, `useBoardTitle` folds a `⚑` glyph into the tab title (a glyph rather than a second count, since tab titles truncate fast; it leads because orders are constant and a request almost never happens), and the panel plays a one-shot entrance animation. All motion is dropped under `prefers-reduced-motion`. The poll's `.catch()` returns `reports: null` as a **failure sentinel distinct from an empty queue** — without it, a broken endpoint would be indistinguishable from "nobody reported anything," silently and forever; `unavailable` surfaces that in the header instead. Resolving is two buttons: "Take it down" calls `DELETE /api/slices` (which clears the report itself — see below), "Keep it" calls `DELETE /api/reports?sliceId=`. `api/slices.js`'s `remove()` calls `deleteReport(id)` so a taken-down photo doesn't leave a request pointing at nothing; `read()` *also* filters reports whose slice is gone, since a slice can expire out from under a live report — note those two are independent, and a test asserting only the filtered response would pass even with the cleanup deleted (`reports.test.js` checks the stored record instead).
- **Rate limits** (`rateLimit()` in `api/_lib/store.js`, fixed-window on Redis INCR): orders 60/IP/10min + 240 global/10min (the per-IP figure is really *per-network* — `clientIp` reads `x-forwarded-for`, and campus wifi puts a whole dorm behind one NAT address, so the building shares that budget; it was 15, which a load test emptied in seconds and which turned away 25 of 40 concurrent orders — see the derivation above `ORDERS_PER_IP` in `api/orders.js`), login 8/IP/5min, slice uploads 5/IP/hr + 60 global/hr, takedown requests 10/IP/hr + 100 global/hr. Friendly 429 messages.
- **No-Redis guard**: on Vercel without Redis env vars, POST /api/orders returns 503 instead of silently storing orders in per-instance memory (where they'd vanish between cold starts).
- **Security posture**: secrets never reach the client (no `VITE_` prefixed secrets, verified against `dist/`); order totals are server-computed; order ids are 10 random bytes (they act as the customer's status read-token); security headers in `vercel.json`, including a CSP. The CSP allows exactly what the site uses: `style-src` needs `'unsafe-inline'` (React `style` props and every GSAP tween write inline styles); `font-src` is plain `'self'` now that the fonts are self-hosted (both Google hosts were removed from the policy when they stopped being contacted); `img-src` needs `data:`/`blob:` (canvas previews on the composer and the share card) and `*.public.blob.vercel-storage.com` (community wall photos). Everything else is `'self'`. Adding an external script, font host, or image host means adding it here or it silently fails to load — test a CSP change by injecting it as a `<meta http-equiv>` into `dist/index.html` and running `npm run preview`, since `vercel.json` headers don't apply locally. No load balancer needed — Vercel's edge handles that.
- **Local dev**: `scripts/dev-api.mjs` mounts the same handlers on :3010; `vite.config.js` proxies `/api` there. Handlers must stay runtime-agnostic (use `readBody`/`readQuery` from `api/_lib/util.js`, not Vercel's `req.body`/`req.query`).
- **Deploy**: `vercel integration add upstash` + set `ADMIN_PASSWORD` in Vercel env vars. `.vercelignore` keeps `.DS_Store` out of the deployment — `.gitignore` isn't enough, because `vercel deploy` uploads the working directory rather than the git index, and Vite copies anything in `public/` into `dist/` verbatim.

### SEO

`public/robots.txt` is hand-written (it disallows `/admin` and `/studio`); `public/sitemap.xml` is **generated** by `scripts/gen-sitemap.mjs` from `PAGE_PATHS` + `BLOG_POSTS` and runs as part of `npm run build`, so a new page or post can't quietly go missing from it. Don't hand-edit the sitemap. Static `og:`/`twitter:` tags live in `index.html` and are the same for every route — link previews show the site card, not the article's own, which is the accepted cost of a client-rendered SPA with no prerender step.

### Lightbox

Global lightbox state (`lbPhotos`, `lbIndex`, `lbOpen`) lives in `App.jsx`. Any page can call `openLightbox(photosArray, startIndex)`. Keyboard (←/→/Esc) and touch swipe are handled inside `Lightbox.jsx`.

**`LB_WIDTHS`/`LB_SIZES` are shared by the rendered `<img>` and the neighbour prefetch, and must stay shared.** The prefetch used to hardcode the 1280 candidate while `sizes` sends a DPR-2 iPad to 1600 and a laptop to 2048 — so it warmed a URL the browser never requested and every arrow press paid a fresh download. The prefetch now sets `srcset`/`sizes` (before `src`, which is what triggers selection) and calls `decode()`, so the neighbour is not just downloaded but decoded before it's needed. The `<img>` also carries **no `key`**: keying it on the photo tore the element down and rebuilt it on every step, so each navigation started with nothing decoded — a blank frame even on a cache hit, plus the entrance animation replaying on every press instead of once on open. `fetchPriority` is spelled camelCase, which React 19 forwards to the DOM. It used to be lowercase because React 18 didn't recognise the camelCase prop and dropped it with a warning — 19 reverses that and warns about the lowercase spelling instead. Either way the failure is silent in effect (the attribute just isn't there and the browser loses the priority hint), so `Lightbox.test.jsx` asserts on the rendered attribute rather than on the source spelling.

**The arrow-key listener subscribes once, via `useEffectEvent`.** `onPrev`/`onNext` arrive as fresh closures on every render of the parent, so listing them in the effect's dependency array detached and reattached the `keydown` listener on each one. `useEffectEvent` (stable since React 19.2) reads the latest callback at call time without joining the dependency list, so the effect runs with `[]`. If you add another handler here, wrap it the same way rather than adding it to the deps. Note that the test for this counts `addEventListener` calls rather than asserting the key works — a "press the key, the handler fires" test passes under the broken version too, since re-subscribing still leaves a working listener attached.

### Animation (GSAP)

Animations run on GSAP (`gsap` + `@gsap/react`, all plugins free since the Webflow acquisition):

- `useScrollReveal` stamps the `reveal` class and drives the rise-in with a ScrollTrigger tween per element (`once: true`); on complete it adds `revealed` and clears inline styles so CSS hover transforms still work. `reveal-delay-N` classes are stagger markers read by the hook — they carry no CSS. Each page uses a fresh instance of the hook (component unmounts on page change).
- **`LineReveal.jsx` splits per line on desktop and not at all on phones.** Below 768px it drops the SplitText path and applies `.line-reveal-rise` — the home hero's own `hero-rise` keyframe — to the whole headline. Three costs stack on a phone and all land during the 260 ms page transition: `autoSplit` can't start until the webfont resolves (line boxes aren't final before then, so nothing is on screen), `SplitText.create` does synchronous layout and injects a wrapper + mask per line, and each line then animates inside an overflow-clipped mask, which repaints rather than composites. Home and the order page always felt faster than menu/blog/gallery for exactly this reason — home uses no `LineReveal` at all and order has a single-line headline. The phone path is a **CSS animation, not a GSAP tween**, on purpose: it runs on the compositor (immune to the contention being avoided), costs no JS on mount, and its `animation-fill-mode: both` guarantees the end state, where a `gsap.from()` applies its hidden start state synchronously and only clears it once the ticker runs. The branch is decided once per mount in a `useState` initializer so the class is present in the first painted frame.
- `LineReveal.jsx` uses the SplitText plugin (`type: 'lines'`, masked, `autoSplit`) for staggered per-line title reveals. It carries every page headline that isn't the home hero: the article title, the Slice Status title, and the hero title + sub on menu, blog, and gallery — those five heroes are meant to read as one entrance, so a new hero headline gets a `LineReveal` rather than a bare `<h1>`. Content arrives either as `text` (a plain string, which doubles as the re-split dependency) or as **children** when the headline carries markup (`<br>`, `<em>` — all three hero titles do). JSX children are a fresh object every render, so a `children` caller must also pass a stable `splitKey`; without it `revertOnUpdate` re-splits and replays the reveal on every unrelated re-render (the menu page re-renders when the 86 list lands).
- **The home hero has no parallax** — it was removed, and `HomePage.jsx` carries the reasoning at the point where it used to live. Short version: sliding a `cover` background inside an over-tall box reads as the photo *zooming* rather than drifting, ScrollTrigger could cache a collapsed scrub range and leave it dead on some loads, and it's a scrubbed transform on a viewport-sized image repainting every scroll frame (already disabled under 768px for that cost). `.hero-img` is `inset: 0` now; the old `-12%` top only existed to hide the drift's edge. The menu and blog heroes (`MenuPage.jsx` / `BlogPage.jsx`) still have the same scrubbed parallax, with an `inset` extending past the top so the drift never exposes an edge — if the zoom reads wrong there too, they come out the same way.
- Every GSAP effect is skipped under `prefers-reduced-motion` (the CSS reduced-motion block makes `.reveal` content visible).

The home hero entrance and the nav hamburger remain plain CSS animations — don't port them to GSAP.

### Typography

Two faces, **self-hosted** from `public/fonts/` and declared in the `@font-face` block at the top of `src/index.css`. They used to load from Google Fonts, which was the largest render-blocking resource on the site (943 ms measured: a DNS lookup and TLS handshake to `fonts.googleapis.com` just to discover the file names, then a second connection to `fonts.gstatic.com` to fetch them). Only the `latin` and `latin-ext` subsets ship; Vietnamese/Cyrillic/Greek were dropped. `index.html` preloads the two latin faces used above the fold — `crossorigin` is required on those preloads even same-origin, or the browser fetches each file twice. Replacing a font means giving the file a **new name**, since `/fonts/*` is cached immutably in `vercel.json`. Note that requesting a narrower axis range from Google returns byte-identical files, so there is nothing to gain by trimming `wght`/`SOFT` to the values actually used (measured, not assumed):

- **`--serif` = Fraunces** — display and body. It's variable on `opsz`, `SOFT` and `WONK` as well as weight. `body` sets `font-optical-sizing: auto` (so the browser picks the text cut at 18px and the display cut at 100px on its own) plus `'SOFT' 25, 'WONK' 0`; the display selector list right below it re-declares `'SOFT' 45, 'WONK' 1`. **WONK is the point of the face** — swashed alternates that look great at hero sizes and noisy in a paragraph, which is why it's opt-in per selector rather than global. Adding a new display heading means adding it to that selector list, or it silently renders in the plain cut.
- **`--ui` = Inter** — every uppercase label, button, price, and bit of meta. A serif can't do small-caps UI at 10–11px; this is the job Garamond was failing at. (`--ui` was called `--mono` back when it held DM Mono.)

**The nav wordmark scales before it disappears.** At its full 20px "Peter's Pizzeria" clears the Order Now button down to ~405px and collides below that. It used to be hidden wholesale at `max-width: 430px`, which took the brand name off every large phone (430px is the iPhone 15 Plus/Pro Max, 412px the Pixel Pro) at widths where it still fit. It now drops to 17px at 430px — worth ~23px, enough to carry it to 390px — and only hides below 390px, where badge + wordmark + CTA + hamburger genuinely overlap however the type is sized. Changing the wordmark size, the CTA padding, or the nav gaps moves that 390px threshold; re-measure rather than assuming.

Uppercase tracking runs on two tokens, `--track-eyebrow` (0.14em, section eyebrows/panel titles/tags) and `--track-label` (0.11em, buttons/meta/chips/sub-lines) — em, not px, so tracking scales with the label instead of drifting tight as type grows. Don't hand-write a px `letter-spacing` on uppercase text; pick a token. No uppercase label goes below 10px.

Eyebrow labels (`.section-label`, `.hero-label`, `.article-tag`, `.article-next-label`) used to lead with a decorative dash, which anchored them and let them sit well away from their title. With the dash gone they read as stray text floating above the heading, so **proximity does the anchoring instead** — a ~9px gap and weight 600, tight enough that label + title parse as one block. Don't loosen that margin back out unless you give the label some other anchor.

`--gold-on-photo` (#E89B4F) is a lighter, warmer gold for type sitting on photography; the base `--gold` reads fine on the ink backgrounds it's used on elsewhere but lands in the same warm brown as the crust on the hero image. `.hero-label` also carries a text-shadow — that, not the lighter color, is what actually holds it against a bright spot in the photo.

Because both faces set wider than the ones they replaced, short fixed strings ("Order Now", "See the Menu") carry `white-space: nowrap` — they wrapped to three lines on a phone without it. The nav wordmark hides below 430px (not 380px) for the same reason.

### Grid tracks

**Equal columns are written `minmax(0, 1fr)`, not `1fr`.** A bare `1fr` is `minmax(auto, 1fr)`, so a track can never be narrower than its content's min-content width — and one unshrinkable child silently steals the other column's space. `.story-grid` had exactly this: `.story-stat` was a four-across flex row (flex items default to `min-width: auto`, so ~525px that could not shrink), which pinned the text track at 525px and squeezed the photo track down to **90px at 769px and 320px at 1024px** — every tablet and small-laptop width, the iPad worst of all. Nothing overflowed, so `body { overflow-x: hidden }` hid it and it looked like a styling quirk rather than a broken track. The stats are now a grid whose cells can shrink, and the story stacks to one column below 900px where two columns leave the text under ~380px. Four stats across need roughly 570px of text column, which is why that layout is opt-in at `min-width: 1400px` and in the stacked tablet block, and 2×2 everywhere between.

Vertical rhythm uses `--gutter` / `--space-xl` / `--space-lg` / `--space-md`, all `clamp()`. Sections differ by weight — story is `xl`, standard content `lg`, strips `md` — instead of the flat 100px/80px they all used to share. The clamps also replace the mobile padding overrides those sections used to need, so don't re-add a `@media` padding rule for a section that already uses a space token.

`StudioPage.jsx`'s share card draws to canvas, which takes the font shorthand only — no variation settings — so the card gets Fraunces' plain (non-WONK) cut. Its `TITLE_FONT`/`MONO_FONT` constants are a separate copy of the type choices; update them alongside the CSS.

## Data

- `src/data/menu.js` — menu categories and items (update prices/items here); an item's optional `special: '<tag>'` field puts it on the homepage specials strip
- `src/data/posts.js` — blog posts array + `ALL_PHOTOS` array for the gallery. `.blog-grid` uses `auto-fit` with a **capped** track (`minmax(320px, 400px)`) plus `justify-content: center`, not `auto-fill` + `1fr` — auto-fill keeps empty tracks alive, which left a single post pinned to column 1 with two ghost columns beside it. Any short row (one post, or the leftovers of a four-post grid) now centres.

## Testing

Automated tests use **Vitest** (`vitest.config.js`, `npm test` / `npm run test:watch`). Test files are colocated with the code they cover (`foo.js` → `foo.test.js`, `Foo.jsx` → `Foo.test.jsx`), not gathered in a separate tree — keep new tests next to the source when adding coverage.

**Two environments, opted into per file.** `environment: 'node'` is the default, because most of the suite is handler and pure-logic tests that never touch a DOM and shouldn't pay for one. A component test opts in with a `// @vitest-environment jsdom` docblock on line 1 and imports from `tests/helpers/dom.jsx`. `vitest.config.js` loads `@vitejs/plugin-react` for the JSX transform — without it esbuild's classic transform looks for a `React` binding none of these files import.

Shared test infrastructure lives in `tests/helpers/`:

- `server.js` — mounts real `api/` handlers on an ephemeral `http` server (mirrors `scripts/dev-api.mjs`) so handler tests hit them with real `fetch()` calls — real headers, streaming bodies, cookies — instead of hand-rolled req/res mocks.
- `env.js` — `resetEnv()` clears Redis/Blob/admin env vars and the in-memory store Maps between tests. **Those Maps are captured in module-top-level `const`s in `api/_lib/slices.js` and `api/_lib/store.js`, read once at first import** — clearing state means calling `.clear()` on the existing Map, not deleting the `globalThis` key and hoping it gets recreated (it won't, within one test file's module registry). Get this wrong and tests pass individually but leak state into their neighbors.
- `fixtures.js` — `placeOrder()`/`adminCookie()` drive real orders and admin sessions through the real handlers; `insertOrder()` writes a synthetic order straight into the store for edge cases (expired, cancelled) that can't be produced deterministically without faking the clock. **It exports `TEST_ITEM_NAME` and `CAPPED_ITEM`, read off `MENU_DATA` by property rather than by name** — an ordinary slice, and whichever one carries its own `maxQty`. Prices and names are validated server-side against `src/data/menu.js`, so a test naming a slice the menu no longer sells gets a 400 ("we did not recognize") that looks exactly like the rejection some of these cases are asserting. Renaming one slice once failed ~50 tests across four files; use these rather than typing a slice name.
- `images.js` — byte-exact minimal JPEG/PNG/WebP buffers built directly from `imageMeta()`'s own parsing offsets in `api/slices.js`, not sourced from real image files. If that parser's byte layout ever changes, these fixtures need to change with it.
- `dom.jsx` — the component harness. Stubs the jsdom gaps the app hits on mount (`matchMedia`, `ResizeObserver`/`IntersectionObserver`, `<dialog>.showModal`, `scrollTo`/`scrollIntoView`, 2D canvas — all of which either throw or print "Not implemented" to stderr), re-exports Testing Library, and provides `mockFetch()` (routes matched newest-first; an unmocked request throws rather than silently returning empty). **Its most important job is the console guard**: anything written to `console.error`/`console.warn` during a test fails that test. React reports key warnings, unknown DOM properties, `act()` gaps, and removed-API deprecations through those channels and then carries on rendering, so without the guard a test asserting only on output stays green while the console fills up. A test that legitimately expects a message calls `allowConsole(/pattern/)` — see `ErrorBoundary.test.jsx`, where the crash log is deliberate.

**What's covered**: all four `api/slices.js` handler branches (auth, quota, rate limits, magic-byte image sniffing, admin moderation, self-delete device auth), `api/orders.js` (the per-item `maxQty` cap — including the aggregate-across-add-on-lines case, not just a single line — and terminal-status transition rejection), `api/nights.js` (auth, revenue totals excluding cancelled/active orders, board-clearing on close, per-order archive detail scrubbed of contact/notes, and archive deletion — admin-only, removes exactly one night, 404s an unknown or already-deleted id, leaves the live board alone, and survives the archive being emptied and reused), `api/_lib/store.js`'s `clearOrders()` (removes exactly the given ids, not whatever's live), the `api/_lib/slices.js` storage layer, `api/reports.js` (unauthenticated POST, per-device count dedupe, admin-only read/dismiss, `devices`/`orderId` never serialized, report cleanup on takedown asserted against the store rather than the filtered response), the route table in `src/utils/routes.test.js` (slug round-tripping, every page id having a unique address, trailing-slash/case/query/hash tolerance, and unknown paths returning null), and the admin session token in `api/_lib/util.test.js` (expiry enforced, backdated timestamps and tampered signatures rejected, password rotation invalidating outstanding sessions), the scrubbing of legacy `contact` values out of public order reads, `responsiveImg`'s fallback width (the `src`, which skips the candidate-list filter that `buildSrcSet` applies, and so could emit a `w` the optimizer 400s on in production only) and the off-site bypass that keeps community-wall Blob URLs out of `/_vercel/image`, and the pure helpers in `src/utils/*.js` (extracted out of page components specifically so they're importable without dragging in React/GSAP/lucide-react — see `src/utils/slices.js`, `src/utils/orders.js`).

**Component coverage** (the jsdom files): `App.test.jsx` — every page id restoring from its own path with the right tab title, article deep links resolving by slug rather than array position, unknown paths falling back to home *and* rewriting the bar, `pp_page2` staying gone, and the landmark contract (skip link first in the tab order pointing at `#main`, `<main tabIndex={-1}>` to land on, nav rendered outside `<main>`). `OrderPage.test.jsx` — the closed card vs. the menu, failing open when the store check errors, and the add-on block: one chip per add-on with the count pinned to `MENU_DATA` (a fifth add-on breaks the 2×2 grid, and this is what says so), name and price in their own elements, Extra Basil priced rather than free, per-unit independence, `aria-pressed` toggling, the aria-label carrying price and sold-out state, `maxQty` and `DEFAULT_MAX_QTY` disabling the stepper, and cart persistence. `Lightbox.test.jsx` — the keydown listener attaching **once** across parent re-renders (asserted by counting `addEventListener` calls, because a test that only checks "the handler fires" passes under the buggy version too), `useEffectEvent` still reading the newest callback, `fetchPriority` reaching the DOM, and the `<img>` staying the same element across navigation. `ErrorBoundary.test.jsx` — fallback instead of a blank page, the crash still reaching the console, and a new `key` clearing the error.

**What's deliberately not covered** (and shouldn't block a PR): the Redis-backed storage path (Lua atomicity, TTL/expiry, list trimming — tests run with no Redis env vars, exercising the same in-memory fallback as local dev), real `@vercel/blob` network calls (mocked via `vi.mock`), and anything requiring a real browser (camera capture, HEIC handling, touch/visibility behavior, actual masonry layout). Those are tracked as a living checklist in **`TESTING.md`** — add to it, don't let it go stale, whenever a feature needed manual poking to trust.

When adding a new API route or a new piece of client logic with real branching, add tests alongside it following this same pattern (real handler + real in-memory store > mocking internals) rather than skipping coverage because "there's no test setup yet" — there is now.

**Never name a menu item in a test.** Derive it — by `maxQty`, by a keyword in its `desc`, by being the first slice. Menu items get renamed and re-described often, and the failure mode is nasty in both directions: a handler test 400s on an unknown item (loud but misleading), while a pure-function test like `addonLabel`'s silently falls down its unknown-item path and keeps passing while proving nothing. That happened — the case guarding against `"Extra Extra Parm"` sat dead until it was re-pointed at whichever slice actually mentions parmesan. Where a case depends on the menu having a particular shape, assert that shape first so it fails loudly instead of vacuously.

`.github/workflows/test.yml` runs `npm run lint`, `npm test` and `npm run build` on every PR and on push to `main`. Two security workflows run alongside it: `semgrep.yml` (fast pattern scanning, seconds) and `codeql.yml` (dataflow analysis, minutes, plus a weekly scheduled run because the query packs improve independently of this repo). Both upload SARIF to the repository's Security tab rather than failing the build. Every `uses:` is pinned to a full commit SHA — a tag can be silently repointed at new code — and Dependabot keeps those pins current. A test that never fails when the logic it claims to cover is broken is worse than no test — when in doubt, prove a new test actually catches the bug it's meant to catch (temporarily break the source, confirm red, revert) rather than trusting that green means correct.

## Static analysis

Three tools, deliberately non-overlapping — ESLint reasons about one file at a
time, Semgrep matches syntactic patterns fast, CodeQL traces values across
module boundaries slowly.

**ESLint** is a flat config in `eslint.config.js`, split into three blocks
because the repo has three environments and they must not share globals: `src/**`
gets browser + React 19 + hooks + a11y, `api/**` and `scripts/**` get Node only
(a `window` or `localStorage` reference in a handler is a real bug, and the
absence of browser globals there is what catches it), and tests get both.
`npm run lint` must come back clean — the script is `eslint . --max-warnings=0`,
and the `=0` is load-bearing: five rules in the config are `'warn'`
(`no-unused-vars`, `no-console`, `eqeqeq`, `prefer-const`,
`react/no-array-index-key`), and plain `eslint .` exits 0 on warnings. Without
the flag the CI lint gate can't fail, and a `console.log` dumping a customer's
order into the production console ships green.

Two settings in there are load-bearing and shouldn't be "tidied":

- **ESLint is pinned to 9.x, not 10.** `eslint-plugin-react` and
  `eslint-plugin-jsx-a11y` both still cap their peer range at `^9`, and this
  repo has already been broken once by a peer split that fails `npm ci` in CI
  before a single test runs (see Dependencies). `.github/dependabot.yml` ignores
  `eslint` majors for that reason — grouping wouldn't help, since the plugins
  have no matching release to travel with and the group would bump `eslint`
  alone anyway. Move to 10 when those two ship support (drop the ignore then);
  nothing else blocks it.
- **`no-unused-vars` sets `ignoreRestSiblings: true`.** `const { contact, notes,
  ...rest } = order` is how `publicOrder`/`publicSlice`/`adminSlice` strip
  fields that must never reach a client. Those names are unused *by design*;
  without this option the linter reports them and invites someone to delete the
  only thing keeping a private field out of a response.

A handful of findings are suppressed inline with the reasoning written next to
them (the index keys in `ArticlePage`/`OrderPage` map over build-time data that
never reorders; the `set-state-in-effect` reports on the admin board and the
community wall are false positives — those `load()` functions await before they
touch state, so nothing is set synchronously). Prefer that over widening a rule.

**CodeQL's remaining alerts are triaged, not fixed**, and the reasoning lives in
`api/_lib/util.js`: the SHA-256 in `checkPassword` is not a stored credential
digest (nothing is persisted or transmitted — it exists to give
`timingSafeEqual` equal-length inputs, and online guessing is bounded by the
login rate limit), and the cookie-parser property write is inherent to parsing
cookies, now on a null-prototype object read only by literal key. Inline
`// codeql[...]` comments do **not** suppress anything — the CLI ignores them.
Dismiss those alerts in the repository's Security tab instead.

## Dependencies

`.github/dependabot.yml` opens grouped PRs weekly (Mondays, ET) for npm and for
the `uses:` pins in `.github/workflows`. The file itself carries the reasoning;
the parts worth knowing before touching a dependency PR:

- **Group order matters.** A dependency joins the *first* group whose rules it
  matches, so the peer-locked pairs are declared above the catch-all
  minor/patch groups. Two pairs are grouped with no `update-types` filter so
  majors travel together: `react` + `react-dom`, and `vite` +
  `@vitejs/plugin-react`. Both are uninstallable if they move apart — `npm ci`
  fails with `ERESOLVE` before a single test runs, which is exactly what
  happened the first time Dependabot split them.
- **`package.json`'s `overrides` block is invisible to Dependabot.** It pins
  transitives up out of known-vulnerable ranges and is maintained by hand. After
  a major on anything owning pinned transitives (`vercel`, the `@vercel/*`
  builders), check `npm ls <package>` — an override pinning *below* what the new
  release ships would silently hold it back.
- **`tailwindcss` majors are ignored.** v4 moves the PostCSS plugin to its own
  package and turns the `@tailwind` directives in `index.css` into an `@import`
  — a migration Dependabot can't perform, and the PR failed the build and would
  have reopened every Monday. Drop the two `ignore` lines when someone wants to
  do it. **`eslint` majors are ignored** for the peer-range reason in Static
  analysis — a solo `eslint@10` PR fails `npm ci` before a test runs. `vercel`
  major/minor is ignored too, for noise: it's the local dev-API
  shim and releases several times a week. Patches still come through.
- Version updates come from that file; **security updates are a separate repo
  toggle** (Settings → Code security), and the `security` group is inert until
  it's on.

## Photos

`photos/` at the repo root holds the **originals** — camera masters, ~134 MB, the input to the script below. They are **not deployed and nothing links to them.** Two folders ship, symlinked individually into `public/photos/` (not `photos/` as a whole, which is what used to drag the originals into every deployment):

- **`photos/large/`** (2400px, q82) — the single source Vercel's Image Optimization API reads from.
- **`photos/static/`** (mixed) — the few images that skip the optimizer.

All image paths in code stay written as `/photos/filename`; the helpers in `src/utils/photos.js` decide which folder and which transform. A path that reaches the browser without going through a helper 404s into the SPA fallback — loud, which is the point.

### Image Optimization

Every `<img>` is a request to `/_vercel/image?url=/photos/large/...&w=…&q=…`, which resizes and re-encodes to AVIF/WebP per device and caches on the CDN (31 days; redeploys don't invalidate). This replaced three hand-built JPEG tiers (640/1600/2400) whose output had to be committed — `sips` can't write AVIF at all, and every quality change meant regenerating and re-committing ~100 MB into git history forever.

- **`responsiveImg(src, sizes, widths, quality?)` is the default for any `<img>` whose rendered width moves with the viewport** — it returns `{src, srcSet, sizes}` to spread onto the tag. Every page image goes through it. A fixed width is wrong in two directions at once: `webSrc` pushed a 1600px file into a 320px card on a phone (the bulk of "photos are slow on my device"), while `thumbSrc` handed 640px to a full-bleed card on a DPR-3 screen that wanted ~1050 and rendered it soft. **The `sizes` string describes the rendered CSS width, so it is coupled to the layout rules in `index.css`** — move a breakpoint or a `max-width` and the matching `sizes` moves with it, or the browser silently picks the wrong tier with nothing failing anywhere.
- `photoSrc(src, width, quality?)` — one photo at one width. `photoSrcSet(src, widths, quality?)` — a full srcset. `webSrc` (1600) is the one fixed-width shorthand left, kept for `StudioPage`'s canvas source, which isn't a DOM image and so can't take part in responsive selection. `thumbSrc` (640) and `largeSrc` (2048) were removed once every page image moved to `responsiveImg` — reach for `responsiveImg` rather than reviving them.
- **Only `/photos/…` paths are optimized** (`isOptimizable`); anything else is returned untouched. The Lightbox is shared between the gallery (app paths) and the community wall (absolute Vercel Blob URLs), and a Blob URL used to come back as `/_vercel/image?url=https%3A%2F%2F…`, which the API rejects unless the host is in `images.remotePatterns` — and nothing is. That was production-only: localhost skips the optimizer, so the wall's lightbox looked fine in dev and served broken images live. Wall uploads are already downscaled to ≤1600px in the browser, so passing them through costs nothing and keeps the allow-list narrow.
- **`OPTIMIZER_WIDTHS` and the qualities must match `vercel.json`'s `images.sizes`/`images.qualities`.** The API rejects any other `w` or `q` outright, and the failure appears only in production. `photos.test.js` reads `vercel.json` and asserts the lists agree — if you add a width, that test tells you what else to edit.
- `images.localPatterns` allow-lists `^/photos/large/.*$` and nothing else, so the optimizer can't be pointed at arbitrary paths on the origin.
- **The optimizer only exists on Vercel.** `optimizerAvailable()` checks the hostname (not `import.meta.env.PROD` — a preview build served from `vite preview` is PROD but has no optimizer) and falls back to the plain source file on localhost. `photoSrcSet` returns `undefined` there rather than a srcset: repeating one file under three width descriptors makes the browser infer a density and lay the image out at a fraction of its real size.

### The static tier

`photos/static/` is served as plain files, deliberately:

- The three CSS hero backgrounds (`.hero-bg`, `.menu-hero-bg`, `.blog-hero-bg`). A stylesheet can't take part in responsive selection, and a query-string URL in `background-image` would break on localhost.
- `og:image` and the LCP `<link rel="preload">` in `index.html`. A social scraper won't follow a transform URL, and the preload has to match the URL the stylesheet actually requests or it's a wasted download.
- The nav logo — under the 10 KB where optimizing stops paying for itself.

Adding an image to this tier means adding it to `STATIC_SPECS` in the script *and* using `staticSrc()` (or a literal path in CSS) to reach it.

### Regenerating

`scripts/gen-photo-derivatives.sh` (macOS `sips`, no deps) builds both folders and **skips files that already exist** — delete a tier folder to force a regen. It then runs `scripts/gen-photo-dims.mjs`, which regenerates `src/data/photoDims.js` (`PHOTO_RATIOS`: original photo path → `w/h`), used by the gallery to reserve each box via `aspect-ratio` so the masonry never reflows. That script takes its skip-list from `DERIVATIVE_TIERS` in `src/utils/photos.js`; without it a new tier folder gets walked as if it held originals and fills `PHOTO_RATIOS` with one junk entry per derivative.

**`sips` gotcha, do not undo:** `-s formatOptions <q>` is silently ignored unless `-s format jpeg` is passed alongside it. sips accepts the flag, exits 0, and writes exactly the bytes it would have written with no quality setting. Every derivative shipped at default quality for this reason — a 640px thumb was 528 KB instead of 88 KB. The script also re-encodes JPEGs already under the target size rather than `cp`-ing them, because several originals are modest in pixels but enormous in bytes. PNGs keep their format (one may need transparency, and changing the extension would break the paths pointing at it), so the four PNG photos are the one place the quality pass doesn't reach.
